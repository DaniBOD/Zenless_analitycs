**Rate:** ~1.8 GB/min de private bytes con OCR activo (~18–48 inferencias/min).

### Síntoma reportado por el usuario (refuerza el eje OCR + spike temprano)
Abriendo la app PRIMERO y el juego DESPUÉS, a veces la app marca **"no responde" por 3–4 min** y
recién ahí arranca. Coincide con que los primeros heartbeats ya marcan ~16 GB: al abrir el juego, el
monitor arranca a OCR-ear sobre pantallas de **carga/transición (S12 → `_deep_detect_s18` cada
frame)** → spike de OCR + leak nativo + presión de paginado → **cuelga la UI thread por minutos**.
Refuerza: (a) gate de OCR debe cubrir S12/deep_detect y pantallas transitorias, no solo S18; (b)
considerar no arrancar OCR hasta que la pantalla esté estable.

## Implicancias para Fase 1
1. **Gate de OCR por frame-diff** (no re-OCR-ear pantalla estática) — mayor leverage: parado en
   S18/S12 era EL driver, y re-OCR de un frame idéntico es puro desperdicio.
2. **Flags `FLAGS_eager_delete_tensor_gb=0` + allocator** — ataca la acumulación nativa per-inferencia.
3. **Watchdog de RAM** (recycle del backend / auto-restart) — acota el remanente.

## ⭐ CAUSA RAÍZ REAL (hallada con priv arreglado) — bug de view en `load_merge`

La hipótesis "leak per-OCR de Paddle" era SECUNDARIA. El driver real es un **balloon de
arranque a ~28 GB en los primeros ~20s de monitoreo**, con `ocr_calls=0` → NO es OCR. Bisección:

```
mss per-call ............ LIMPIO (150 iters, priv plano)
classify ................ LIMPIO (120 iters, priv plano)
AgentIdentifier() ....... 28 GB  ← acá
load_merge (bisección):
  row  (336 refs) → +7.2 GB
  badge(470 refs) → +14 GB
  det  (316 refs) → +6.3 GB
```

**Bug** (`avatar_descriptor.py::load_merge`): `AvatarDescriptor(data["ncc"][i], ...)` dentro del
loop. `data["ncc"]` **recarga la array COMPLETA** (N×12288, ~23 MB) del npz en cada acceso, y
`[i]` es una **VIEW de numpy que mantiene viva esa array completa**. Con N refs → N copias
completas retenidas (~25 MB/ref). Las arrays crudas pesan 74 MB en total, pero se inflaban a
28 GB. Invisible a tracemalloc porque numpy usa malloc directo (pyheap quedó plano). Empeoró al
crecer las librerías (cap badge 6→10 + librería de detalle nueva).

**Fix:** leer cada array UNA vez fuera del loop + `.copy()` de la fila → cada descriptor guarda
su fila chica y las arrays completas se liberan. **Resultado: 28 GB → 155 MB (~180×).**

```
AHORA: row→403MB  badge→435MB  det→455MB  |  AgentIdentifier() → 537 MB
```

Este bug ya causaba el RNF-06 original (doc 2026-06-12: ~12-14 GB con la librería badge sola).

## (Histórico) Nota de instrumentación original
El heartbeat logueó **WorkingSet**, que Windows **recorta** al paginar cuando la app está en
background → la serie baja (16→12 GB) y el net-rate dio un falso "sin fuga". El **private bytes**
es el metric monótono correcto. Fix: agregar private bytes al heartbeat + ajustar el veredicto de
`tools/parse_mem_diag.py`. Necesario para curvas limpias antes/después en Fase 2.
