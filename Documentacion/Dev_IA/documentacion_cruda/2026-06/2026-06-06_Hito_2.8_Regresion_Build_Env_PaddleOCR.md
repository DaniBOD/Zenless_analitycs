> **Sesión:** 2026-06-06
> **Branch base:** `main`
> **Owner:** DaniBOD (con asistencia IA)
> **Scope:** Diagnosticar por qué el `.exe` extraía stats S18 de forma volátil/lenta (ER
> que no aparecía, Prob. Crítico oscilando) pese a tener el código correcto, y cerrarlo de
> raíz. Spoiler: **no era el parser — era el Python con el que se construía el `.exe`.**

## 0. TL;DR

El `.exe` venía extrayendo los stats de "Atributos base" (S18) de forma **no-determinista**:
el `recuperacion_energia` (ER) tardaba ~20 ciclos en aparecer o no aparecía, el Prob.
Crítico oscilaba entre `19.4%` y `194%`, e Impacto/Tasa Anomalía/Daño Crítico leían valores
con dígitos de más (`98↔928`, `96↔926`, `64.4↔644`). El usuario reportó "**no sucedía
antes**".

**Causa raíz:** `tools/rebuild.ps1` invocaba `python -m PyInstaller` con el `python`
**pelado**. Por el *App Execution Alias* de Windows, ese `python` resuelve al **Python de
Microsoft Store** cuando el `.venv` del proyecto **no está activado** (p.ej. tras reiniciar
la PC). Ese entorno tiene **numpy 2.3.5** (incompatible con paddle), **torch** (bloat) y
**paddleocr NO instalado** → el `.exe` se empaquetaba con un PaddleOCR degradado/no-
determinista. El build determinista del 2026-05-31 (33.6 MB, `missing=[]` a la primera) se
había construido **desde el `.venv`** (numpy 1.26.4 + paddleocr 2.8.1 + paddlepaddle 2.6.2).

**Por qué costó verlo:** todos los tests y diagnósticos *offline* pasaban, porque usan el
paddle limpio de `D:\paddle_site` (numpy 1.26) vía el `sys.path` del `conftest`. El `.exe`
era el único que veía el paddle roto. Se persiguió el síntoma en el regex del ER (parser)
durante varias builds antes de mirar el **entorno de build**.

**Fix:** `rebuild.ps1` ahora apunta **directo** a `.venv\Scripts\python.exe` (con fallback a
`python` + warning) y agrega un **guard** que aborta si el intérprete no es `numpy 1.x` con
`paddleocr`. Ya no depende de que el `.venv` esté activado en la terminal.

**Validación:** build #25 = **33.7 MB, sin torch** (vs 74.3 MB con torch del build roto) →
idéntico al build determinista del 05-31. OCR estable en juego confirmado por el usuario.

## 2. Diagnóstico — descartando el código

1. El mismo `parse_agent_stats` corrido **offline** sobre un frame capturado en vivo (mismo
   pipeline mss vía `tools/diag_ocr_live.py`) extraía `ER=1.2` perfecto. → el parser está bien.
2. El `.exe` (mismo código) fallaba. → la diferencia está **fuera del código**: el OCR.
3. Comparación de entornos (`importlib.util.find_spec` + `numpy.__version__`):

   | | `python` pelado (build) | `.venv` del proyecto |
   |---|---|---|
   | Intérprete | Windows Store | `.venv\Scripts\python.exe` |
   | numpy | **2.3.5** (rompe paddle) | **1.26.4** ✅ |
   | paddleocr | **NO** | **SÍ** ✅ |
   | paddle | (vía D:\paddle_site, no default) | **SÍ** ✅ |
   | torch | **SÍ** (bloat) | NO |
   | PyInstaller | 6.20.0 | 6.20.0 |

4. `tools/rebuild.ps1` línea ~60 usaba `python -m PyInstaller` (intérprete ambiente). El
   lesson del `Dev_IA/2026-05-31_Migracion_Python_PaddleOCR.md` §2.1/§7 ya advertía el gotcha
   del App Execution Alias y recomendaba "buildear desde el venv" — pero `rebuild.ps1` no lo
   reflejaba.
5. **Trigger humano (capa 8):** el usuario apagaba la PC al ir a comer/dormir, lo que cerraba
   la **activación** del `.venv` en la terminal. Builds post-reinicio → `python` = Store →
   `.exe` roto. Builds con venv activado → OK. De ahí la intermitencia "a veces sí, a veces no".

**Evidencia de bundle:** el build roto pesaba 74.3 MB y empaquetaba `torch`; el bueno (05-31)
pesaba 33.6 MB sin torch.

## 3. Fix implementado

**Archivo:** `tools/rebuild.ps1` (commit `d92dd61`).

- **Selección de intérprete:** `$venvPy = $repoRoot\.venv\Scripts\python.exe`; si existe →
  `$py = $venvPy`; si no → `$py = "python"` con `Write-Warning` rojo. Todas las invocaciones
  de PyInstaller usan `& $py -m PyInstaller ...`.
- **Guard anti-regresión** (antes de buildear):
  ```powershell
  & $py -c "import numpy, importlib.util as u; ok = numpy.__version__.startswith('1.') and (u.find_spec('paddleocr') is not None); print(numpy.__version__ + '|' + ('OK' if ok else 'BAD'))"
  # si no termina en '|OK' → exit 1 con instrucciones de reinstalar paddle en .venv
  ```
- **Beneficio:** el build **ya no depende de activar el `.venv`**. Funciona recién reiniciada
  la PC, y si el `.venv` se rompiera, el guard frena en vez de armar un `.exe` degradado en
  silencio.
- **`app/build/main.spec` no se tocó** — ya hace `collect_all("paddle"/"paddleocr"/...)`; el
  problema era el intérprete desde el que corría PyInstaller, no el spec.

  ```

  12:38:23 [reconocido] Soukaku (por avatar)
  ```

  Nótese que el latch heredado (S18→S8) **sí** funciona los primeros frames, e incluso engancha
  "Soukaku (por avatar)" una vez (12:38:23), pero después **pierde** el latch y cae a "sin

- **🐛 BUG de estado del parser — el fallo de un PJ contamina a otros ya reconocidos (2026-06-06):**
  cuando se dispara el bug anterior (PJ en esquina del slider sin reconocer), **altera el estado de
  otros PJs que ya estaban bien reconocidos**. El usuario tuvo que **parsear una segunda vez** para
  re-estabilizar el roster reconocido y esquivar el problema. Esto apunta a estado **compartido/global**
  en el identificador o el aggregator que no está aislado por PJ: un frame "sin identificar" o un
  embedding degradado estaría pisando/invalidando latches previos en lugar de quedar contenido a la
  celda activa. **Pendiente:** auditar dónde vive el estado de "PJ reconocido" (¿un único latch global
  en `monitor`/`controller` vs. un dict por avatar-hash?); el fallo de identificación de un PJ no debe
  mutar el resultado ya confirmado de otro. Relacionado con el bug del slider (mismo origen probable:
  el latch global se ensucia). Prioridad media-alta — corrompe data ya buena y obliga a re-parsear.

- **Brecha B5 (avatar-row oculto) — propuesta del usuario: latch al último PJ reconocido (2026-06-06):**
  en S8 (Equipamiento) si se detecta el PJ por avatar y luego el usuario **oculta la fila de avatares**
  (auto-hide del juego), la identificación **se cae** ("sin identificar"). El usuario propone, como
  mínimo viable, **conservar el último PJ reconocido** mientras la pantalla siga siendo S8 del mismo
  contexto, en vez de degradar a "sin identificar". Esto es exactamente la vía (b) del bug del slider y
  cierra la B5 de forma honesta sin necesidad del modelo 3D (descartado) ni embeddings aprendidos:
  **mantener el latch del último PJ confirmado en S18/por-avatar** y solo soltarlo ante un cambio de
  pantalla "duro" (volver a roster, cambiar de PJ con avatar visible y distinto, etc.). Es la solución
  unificada para los tres ítems de arriba: un **latch persistente por contexto** que (1) no se cae al
  ocultar la fila, (2) no se pierde en PJs de esquina, y (3) no contamina a otros PJs.

## 7. Lecciones aprendidas

- **Síntoma solo-en-`.exe` ⇒ mirar el entorno de build, no la lógica.** Los tests con el paddle
  limpio (`D:\paddle_site`/`.venv`) enmascararon la regresión del bundle durante varias builds.
- **Nunca depender de "activar el venv".** Un script de build debe apuntar al intérprete del venv
  por ruta absoluta + verificar el entorno (guard), no confiar en el `python` ambiente.
- **El tamaño del artefacto es una señal barata.** 74 MB vs 33 MB (torch presente/ausente) gritaba
  "entorno equivocado" antes de cualquier análisis fino de OCR.
- **Reiniciar la PC cierra activaciones de shell.** Cualquier flujo que dependa del estado de la
  terminal (venv activado, env vars) se rompe tras un reboot; preferir rutas absolutas.

asignado es el **avatar circular a la derecha de "Nivel X/15"**, cuyo Y se desplaza con el largo
del nombre del set. Es un indicador **por disco** (el grid muestra discos de otros PJs).

**Hallazgo empírico (medido sobre 7 crops reales 2557×1439):**
- Matchear el avatar **circular** S17 contra la librería del row (S18) **se rompe**: todo colapsa
  a "Miyabi" ~0.58 (el fondo rayado de las esquinas domina el descriptor rectangular).
- Descriptor **circular enmascarado propio** (esquinas anuladas): same-PJ **0.95–0.99**, otro PJ
  **≤ 0.76**. Separación limpia con umbral **0.86**.

**Diseño elegido (híbrido latch + guarda):**
- Fuente de identidad = **latch** (`_last_agent_name`, PJ cuya pantalla se ve; ya confiable y
  preservado a través de S17). Correcto para el flujo dominante (parsear los discos de un PJ).
- **Guarda por avatar:** librería S17 propia (`avatar_library_s17.npz`) bootstrapeada del latch.
  `s17_similarity(face, latch)` ≥ 0.86 ⇒ confirma; < 0.86 ⇒ el avatar es de OTRO PJ (disco del
  grid) ⇒ **abstener** (no escribir, preservar lo curado, RNF-02). Primera vez del PJ ⇒ confiar

- **Persistencia ENFOCADA** (sin scoring, decisión del usuario): `DiscSyncer.persist_s17_disc`
  hace upsert disco + asignación con salvaguarda (`update_from_parsed` nunca pisa
  `agente_asignado`/`equipado`; `update_assignment` solo con match confiable). Bono de conjunto
